## Rules that bind

New names (frame kinds, classes, custom properties) have none of impl, rev, judge, fix, test, accept, implement, review, reviewer, fixer as a whole word, and no quoted string 'fix', 'judge', 'verify', 'guide' (test/integration/universal.test.mjs, and the scan in web-u4).
- contract section 1, "Replay inside the real server": "Pause is the client's: it stops applying the stream's frames (`run`, `event`, `end`) and keeps them, in order. Resume plays the kept frames with the gaps they arrived with, never in one burst: from then on the view runs behind the stream by the paused time, and frames that arrive meanwhile queue behind the kept ones". And: "A stream that fails or closes while frames are kept loses none of them: they are played (or stay kept while paused), and the failure line is shown after the last of them." Section 4: "After `hello` there is no frame for a failure: a stream that ends without `end` is shown by the UI as lost"; the `run` snapshots come "same throttle".
- AGENTS.md, Hard rules: "Never invent data": pacing is only what the page measured (arrival times), never the event ts, never a default delay, minimum gap or cap; "The visualizer only observes"; "Write only the files your node owns"; no git commit, stash or reset; ES modules, zero npm dependencies; roles, phases and labels "come from run data, never hard-coded".
- graph.md section 9: "Workflow agents must stop only the processes they started, by PID"; "Two modes of tracking (user, 2026-11-10)": the hint "must not block or change the agent's work", so item 7 adds a mark only: no behaviour, no listener, no new text. Never the browser pane (task rule).

## Traps
- Item 1, the queue. Pure in lib.js; inject now, setTimer, clearTimer and apply; app.js passes `() => performance.now()` and arrows that look up setTimeout and clearTimeout when called, so a test's fakes are used. Stamp a frame when the page reads it from the stream, not when it is applied, never from its ts. Store the arrival time, not a due time: due = arrival + total paused time is computed when needed, so a second Pause (it adds to the offset at its Resume) moves every kept frame at once. Decision: a frame is applied at once only when nothing is kept and its due time is not in the future. With no pause the offset is 0: no timer, no delay, as today. After a pause the offset stays (contract: "from then on the view runs behind the stream by the paused time"), so a later frame is still behind by it and the gaps stay the arrival gaps. **The spec's first sentence ("while playing with nothing kept, a frame is applied on arrival, no added delay") is therefore true only until the first Resume; the user is to confirm this reading.** It also holds when the queue was empty at Resume, and the control offers Pause already while the phase is 'connecting' (preparing a big run can take seconds): measured on the code, a replay in 'connecting', Pause at 100, Resume at 10100, hello and event 1 at 10100: event 1 is applied at 20100 (one timer of 10000), although the view was never behind. The code follows the contract sentence and the test "pause: a resume with nothing kept still counts the time paused" asserts it; changing it (no offset when nothing was kept) is a change of the contract's sentence, for the user, not for the implementer. Resume applies in order, in one pass, every frame already due, then arms ONE timer for the next; clear before arming, on Pause, on every drop; the callback re-checks that its replay is the one on show. One queue per replay (a reused one carries the old offset and timer). Stop, a run switch and Replay again all end in dropReplay: it clears queue and timer. Add one window `pagehide` listener that calls it. An exception inside an apply in the timer is a failure line (failReplay), never an uncaught error that breaks the chain of timers.
- Item 2. A snapshot is a frame like the others. Drop the older of two snapshots only when they are neighbours in the queue (nothing between, not even `end` or a failure marker); the newer keeps its own arrival time; the last snapshot before `end` stays. While playing with nothing kept nothing is dropped. No cap and no other drop (a long pause keeps every snapshot that has an event before it: the user's decision, say it in the note, do not add a limit).
- Item 3. `rep.endSeen` is set at arrival so a stream that closes after `end` is not "cut"; it never drives the control. The phase becomes ended only when the end frame is applied from the queue (endReplay). Until then the control is Pause or Resume, and Stop; "replay finished" is not written at arrival. The same when `end` arrives while the kept frames are playing (phase playing, the queue not empty): it is queued behind them, due at its arrival time plus the offset, and the button says Pause until it is applied.
- Item 4. `rep.closed` must mean "the replay was left" (Stop, switch): callbacks of a left replay do nothing and the queue is cleared. A stream that fails is not a left replay, but today failReplay sets closed, aborts and calls buffer.take() (read): all three lose frames. Decision: a failure known when a frame arrives (the reader throws, the stream ends without `end`, data that is not JSON, a snapshot that is not the replayed Run: replayRunProblem is pure) becomes a last frame in the queue (its own kind) and the reader stops; the line is made when that frame is applied, then the phase is failed. The same holds while the kept frames are playing (phase playing, the queue not empty, Resume was pressed): a failure, a cut, `end` or a snapshot that arrives then goes behind the kept frames, due at its arrival time plus the offset, and is shown at its own turn, never at arrival (the test "catching up: ..." sends six such arrivals at t=650 with frame 3 still kept and checks nothing changes before 1150). A failure found at apply time (state.log.push says gap) is failReplay at once and clears the queue (frames behind a broken order are not shown: a snapshot, an event that is valid by itself and the end behind the gap must never be applied, and the end must not turn the failure into "replay finished"; the out-of-order test sends all three, because events behind a gap are gaps themselves and prove nothing). With nothing kept and no offset a failure is applied at once, as the errors tests expect. Failures before the hello (a refusal, a wrong hello) are immediate: nothing is kept. Pause and Resume work while the failure frame is kept; Stop drops it. The line goes through setText: a markup in a reason stays characters (existing test).
- Item 5. replayCutText(count) must get the events applied when the failure frame is applied, never the number received. `rep.count` grows only in applyReplayEvent. After Resume the button says Pause as soon as the phase is playing, also while frames wait; replayControl stays pure.
- Item 6. replayControl reads `replay.real` for a failed replay. A replay that never began (`shown` false) keeps the Run that was on show at the click: keep rep.real at the current real Run where the real snapshot is applied, and leave a shown replay's alone (the real stream is ignored then). Missing values, unchanged rule: a real Run with no source gets no Replay control; an unknown status (null value) gets it; only the value "running" does not. The flash timer (FLASH_MS + 30 = 1530 ms) removes `flash` from matrix and timeline nodes when it fires: on Pause cancel the pending ones (one handle per agent in one Map, `state.flashEnds`, cleared on Pause and on drop; armFlashEnd cancels the handle it replaces: two events of an agent at the same page time left an older timer that Pause could not reach, its callback passed the `state.flash.get(id) !== t0` guard and took the highlight off while paused; a reviewer's probe: one timer left after Pause, one write to the centre view at expiry; measured on the fix: the new test turns red when the cancelling line is removed) or hold them and sweep on Resume; a MutationObserver over the centre view sees no record between Pause and Resume, even when every recorded timeout is run. No further `setTimeout(` text beyond the queue's (4 in all).
- Item 7. Static markup only: an inline svg in the header button and in the h2, `aria-hidden="true"`, `focusable="false"`, width and height 14, no `<title>`, no aria-label, no role (a title inside would change the accessible name). The fill is set in CSS from `var(--warn)` (already #f5c542 in :root with the other function colours; a new variable goes on that line), the "!" from var(--bg); no hex in a `.hint` rule; class names `warn` and `icon` only. **In the header button the sign must take no room in the line**: `.hint-open` is `position: relative` and `.hint-open > .icon.warn` is `position: absolute; left: -7px; top: -7px; margin: 0`, so the sign hangs over the button's top-left corner and the button keeps its width; in the h2 it stands in the line before the text (`.icon.warn`: margin -2px 5px -2px 0, vertical-align -2px). Why (measured, headless Chrome, a run on show, the sign in the line): it made the button 19 px wider (123.1 against 104.1 px), and for viewport widths of about 796 to 815 px that moved the button to a row of its own: header 108.77 px against 78.58 px at 800 px wide. Any width the sign takes from the line has such a window for some run, so the only fix that holds for every run and width is no width at all. Baseline (measured, headless Chrome, no run on show): header 45.19 px high at 800 and 1228 px wide; the button 104.1 x 21.4 px, font 11 px. Measure again at both widths, and the notice at its 420 px maximum: header height unchanged, the button 104.1 px wide with and without the sign, the sign over the button's corner (not inside its line), title and sign wrap together with no overflow. Measured on the fix: with the sign shown and with it `display: none` the header height is the same at every viewport width from 320 to 1300 px (step 4), for two runs, and with 0 to 400 px of extra width added to the status (step 2); no horizontal scroll; the button is 104.1 px either way.
- Item 8 and escaping: no innerHTML in the replay code; strings through setText or esc(). Resume must not call applyRun with a held Run (a whole re-render); it applies frames only. Pause and Resume write only the control's buttons (setShown, setText).

## How to check each item by hand

1. Fake clock: arrivals 0, 100, 400, Pause at 50, Resume at 1050: applied at 0, 1100, 1400. A second Pause of 500 during catch-up moves every kept frame by 500; a frame arriving at 1200 is applied after the kept ones, behind by the whole paused time. No timer is made in 100 frames with no pause.
2. Snapshot, event, snapshot, `end`: applied in that order; two neighbouring snapshots: the older is gone; an event between them: both stay.
3. `end` last: no "replay finished" before it, also when stream.end() follows `end` at once, and also when `end` arrives while the kept frames are playing (Resume pressed, a frame still kept): the button says Pause and no line shows until `end`'s own turn (arrival + offset).

Same with stream.fail('x') and with a close and no `end`: frames played, then 'x' or "stream ended before the end (N events played)" with N applied, then Replay again and Stop; Pause and Resume work until then; Stop mid-queue leaves no timer.
