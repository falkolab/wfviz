# Node guide: tracking hints (unit tracking-hints)

Read with docs/guides/common.md (unchanged by this node): [stale-test] (test/index.js lists suites, see below), [weak-test] (mutate before you issue a test), [guide-defect] (a value the code branches on that can be missing gets one sentence), [doc-mismatch] (every command and option the README gives is checked against the page and `--help`; the page's documented cautions go into the README; "not documented" only after the page was searched). Not docs/guides/tracking-hint.md (singular: the web notice). The spec (items 1-6) is in the node task; this file says what binds, what you own, where it goes wrong, and how to check. Docs were fetched 2026-11-11; the plugin reference now sits under /docs/en/plugins/ (manifest-reference, components, install, cli-reference). Re-read them before you write.

## Rules that bind
- docs/contract.md, intro: "wfviz is universal"; no role, phase, label, node code, file name or result shape of our method "may be required or hard-coded". test/integration/universal.test.mjs scans src, web, bin only (DIRS), not plugin/: your own test does the scan of plugin/.
- contract section 3: "Recognition is by field names only". The text may name only fields that section lists: verdict, reason, findings, file, line, severity, description, tests, passed, failed, skipped. Section 2: "`round` comes only from `#r<n>`"; the label pattern is "inferred, never required".
- AGENTS.md, Hard rules: "Never invent data."; "Do not use API, hooks or log formats that are not documented or observed. Check first."; "Write only the files your node owns."; "No global config changes, no plugin installs, no publishing in this stage."; "ES modules, Node >= 20, zero npm dependencies."; no git commit, stash or reset.
- graph.md section 9, "Two modes of tracking": the hint is "advisory" and "must not block or change the agent's work"; "A node's gate can block on a test outside its owned paths that asserts the old contract"; stop only processes you started, by PID.

## Documentation lines relied on (plugin pages, hooks page)
- Manifest: "`name` is the only required key."; it sits at `.claude-plugin/plugin.json`; "Put every other plugin file at the plugin root, not inside `.claude-plugin/`. That includes `skills/`, `commands/`, and `hooks/`."; an unrecognized top-level key "is stripped".
- Hooks file: "Save the plugin's hooks in `hooks/hooks.json` at the plugin root, under a top-level `"hooks"` key"; a file without that wrapper "fails to load"; "Claude Code merges whatever you declare with `hooks/hooks.json`": a `hooks` key in plugin.json as well would register the hook twice.
- Exec form: "A command hook runs as exec form when `args` is set"; example `"command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/scripts/format.js", "--fix"]`; placeholders "are substituted into `command` and into each `args` element as plain strings".
- SessionStart: matcher table row "how the session started": `startup`, `resume`, `clear`, `compact`, `fork`; source "`startup` for new sessions"; a plain-word matcher is an "Exact string, or list of exact strings separated by `|` or `,`", so `startup` does not match `fork` or `resume`.
- Output: `additionalContext` is a "String added to Claude's context at the start of the conversation, before the first prompt."; the docs' example is `{ "hookSpecificOutput": { "hookEventName": "SessionStart", "additionalContext": "..." } }`. Left unused: `initialUserMessage`, `sessionTitle`, `watchPaths`, `reloadSkills`, `continue`, `stopReason`, `suppressOutput`, `systemMessage` (the docs do not require it).
- stdout: it "counts as JSON output only when you print one JSON object, on one line or several, with nothing around it but whitespace"; a SessionStart hook's plain-text stdout is also added to context, so a stray line becomes advice. Exit 2 on SessionStart "Shows stderr to user only"; other codes are non-blocking; strings are "capped at 10,000 characters" (the hint is 609 characters, measured). stdin: "For command hooks, this JSON arrives via stdin" (session_id, transcript_path, cwd, hook_event_name, source, model).
- Option: "`userConfig` declares values Claude Code prompts the user for when the plugin is enabled"; fields `type`, `title`, `description` (required), `default` ("Value used when the user provides nothing: a string, number, boolean, or array of strings"); "An unknown key fails validation"; "`CLAUDE_PLUGIN_OPTION_<KEY>`: exported to hook processes for every option, with `<KEY>` uppercased". So `trackingHint` arrives as CLAUDE_PLUGIN_OPTION_TRACKINGHINT. Values are set in `/plugin configure <plugin>@<marketplace>` ("To open the same dialog at any time, the user runs `/plugin configure <plugin>@<marketplace>`") or with "`--config KEY=VALUE`" at install; "The `claude plugin install` shell command never prompts". After install the shell command is `claude plugin configure <plugin>@<marketplace>`, which "Requires Claude Code v2.1.285 or later": without flags it "lists each option with up to three labels" (`required` or `optional`, `set` or `not set`) and "prints no saved values", so it saves nothing; saving is `--values-stdin`, "Read option values from stdin as a JSON object of single-line strings and save them. Options you leave out keep their saved values" (components page: "pipe a JSON object to `claude plugin configure --values-stdin`"); a saved value prints "Restart Claude Code to apply it"; `--json` adds the saved values of options that are not sensitive. `claude plugin configure --help` (2.1.306, 2026-11-11) says the same: "Show a plugin's options and which are unset, or save values from stdin with --values-stdin". The Installed tab of `/plugin` offers "Configure options" when the manifest declares `userConfig` options. The pages give no example of a boolean value as a string: the README says so and tells the user to read the value back.
- Try and install: "`claude --plugin-dir ./my-plugin`" (one session); "`/plugin install <plugin>@<marketplace>`"; "`/plugin marketplace add ./my-marketplace`" needs `.claude-plugin/marketplace.json` with `name`, `owner`, `plugins`.
- Hooks page, `additionalContext` (searched 2026-11-11), documented cautions: "Claude Code wraps the string in a system reminder and inserts it into the conversation at the point where the hook fired. Claude reads the reminder on the next model request, but it doesn't appear as a chat message in the interface."; "Write the text as factual statements rather than imperative system instructions."; "Text framed as out-of-band system commands can trigger Claude's prompt-injection defenses, which causes Claude to surface the text to you instead of treating it as context."; "To confirm delivery, check the debug log." The approved text is imperative and cannot be reworded in this node: the README states the caution so the user decides knowingly, and the note repeats it.
- Not documented, build nothing on it: the string a boolean option takes in the environment; whether an option with a default but no saved value is exported; whether the model follows the context (the page says only that Claude reads the reminder); whether a boolean option takes the string "false" in `--config` or `--values-stdin` (the pages say values are validated against the declared type, with no boolean example).

## Files you own and the shared tests
- Own: plugin/ (.claude-plugin/plugin.json, hooks/hooks.json, scripts/session-start.mjs, README.md) and test/plugin/ (index.js shim like test/server/index.js, *.test.mjs). Nothing under src/, web/, bin/, docs/.
- Hidden test gap, outside owns: test/index.js lists the suites by name ('source', 'model', 'server', 'demo', 'integration', 'workflows') and imports each suite's index.js. On Node >= 21 (here: v26.0.0) `npm test` runs test/index.js, so test/plugin/ never runs unless 'plugin' is added. A listed suite without test/plugin/index.js crashes the whole run. The orchestrator either adds test/index.js to owns (one word added; index.js created first) or makes that edit right after the node writes test/plugin/index.js. The note must show `node --test test/` pass count rising by the plugin tests; "pass" without that is a [stale-test] finding. package.json needs no change. A fixer for this node does not own test/index.js either: it names the one-word edit (add 'plugin' to the suites array) in its note as the orchestrator's open item and does not make it.
- grep of test/ for plugin, hooks, additionalContext and the repo's top-level listing found no assertion on what this node adds: this node makes no other test fail. Baseline measured 2026-11-11 at HEAD 003a8ac, per suite (`node --test test/<suite>/`): demo 46, workflows 176, model 266, source 178, integration 40 (all pass), server 498 with 496 pass, 1 fail and 1 cancelled: the two web log tests "log count: showing the last 2000 of 2060 events..." ## Traps
1. Invented values: plugin.json holds `name` "wfviz", `description` and `version` copied from package.json, `userConfig`. No author, email, license, homepage, repository (no source gives them). userConfig.trackingHint has exactly `type` "boolean", `title`, `description`, `default` true: any other key stops the plugin from loading.
2. Coupling: scan every file under plugin/ and the test's literal for guide, judge, fix, reviewer, implement, dev-graph, graph.md, AGENTS, docs/, and node codes /\b[A-Z][0-9]{1,2}\b/ (the text's "r2" is lower case and passes). The text says "role" and "phase" as generic words; do not reword it.
3. Exact text: one constant in the script, LF between lines, no leading or trailing newline, bullets "- " at column 0, straight quotes, ASCII only. Strip exactly the harness indent from the task text. The test holds its own literal copy, parses stdout and compares the string (JSON.stringify escapes quotes and newlines).
4. One object only: a single process.stdout.write of the JSON and "\n"; no console.log, no second write. Test keys at both levels: ["hookSpecificOutput"] and ["hookEventName","additionalContext"].
5. Exit 0 always: wrap main in try/catch, set process.exitCode = 0, never call process.exit before the write is done, never exit 2. Decision to name: the script does not read stdin (the docs' own example commands never read it); the tests still feed empty, `{bad`, 1 MB of bytes and a closed stdin, and require the hint and exit 0.
6. No file, no network: the script imports nothing (no node:fs, net, http, https, dns, child_process, no fetch(, import(, require(); the test greps its source for them) and reads one env variable.
7. Off switch: the docs define userConfig, so it is used and WFVIZ_TRACKING_HINT is not built (a test sets it to "off" and still expects the hint). CLAUDE_PLUGIN_OPTION_TRACKINGHINT, trimmed and lower-cased, "off", "0" or "false": stdout is empty (0 bytes), exit 0. Unset, empty, "true", "1", garbage: the hint (a missing value counts as on). Tests delete both variables from the child env first, so the developer's own env cannot change a result.
8. Hooks config: only the SessionStart key, one group with "matcher": "startup", one handler `{ "type": "command", "command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/scripts/session-start.mjs"] }`, top-level "hooks" wrapper; no `hooks` key in plugin.json (twice-registered hint); the script does not read `source`: the matcher is the only filter. The test replaces ${CLAUDE_PLUGIN_ROOT} by the absolute plugin/ path, checks the file exists, and spawns that command and args.
9. README: what it does, the one-session command `claude --plugin-dir ./plugin`, the install steps only as the pages give them (`/plugin marketplace add`, `/plugin install wfviz@<marketplace>`), the off switch (the `trackingHint` option: in a session `/plugin configure wfviz@<marketplace>`; at install `--config trackingHint=false`; afterwards `echo '{"trackingHint": "false"}' | claude plugin configure wfviz@<marketplace> --values-stdin`, Claude Code 2.1.285 or later; the bare `claude plugin configure <id>` is never offered as a way to set, it only lists), "never blocks" (exit 0, no decision field). plugin/ gets no marketplace.json: it needs an owner name and no source gives one; say in the note that the user decides. It does not promise the model follows the hint, and it states the documented caution: the text goes into a system reminder that is not shown as a chat message, and imperative wording can make Claude show it to the user instead of using it; the approved text is mostly imperative, so the risk applies. Its test checks the README against these pages (every `claude plugin configure` line carries a flag; the piped JSON holds a string value), not against its own sentence. Never run claude --plugin-dir, install, enable or marketplace add. `claude plugin validate ./plugin` is the docs' manifest check: run it only if claude is on PATH and quote its output.
10. Weak tests: before issuing, break each on a throwaway copy and see it fail: one character of the text, "severities" added to the fields line, a second output key, exit 2, matcher "startup|resume", a `hooks` key in plugin.json, a `systemMessage`; in the README: the bare `claude plugin configure` bullet back, `--values-stdin` dropped from the piped line, a boolean instead of a string in the piped JSON, the version dropped, "saves nothing" or the caution sentences dropped.
11. Brittle tests: on a Mac the folder gets `.DS_Store` (also `._*`, Thumbs.db, desktop.ini) from Finder or an editor, and .gitignore expects it. The helper `listFiles` skips exactly those names, so the four-file test and the text scans do not go red or read a binary file as text; any other extra file (marketplace.json, `.env`, a second script) is still listed and fails the four-file test. A test proves both on a copy of plugin/.

## How to check each item by hand (no Claude session needed)
1. `echo '{"source":"startup"}' | node plugin/scripts/session-start.mjs; echo $?`: one JSON line, exit 0; parse it and compare the text with the spec.
2. `CLAUDE_PLUGIN_OPTION_TRACKINGHINT=false node plugin/scripts/session-start.mjs </dev/null | wc -c` gives 0; also off, 0, OFF; true and unset print the hint.
3. Same script with `</dev/null`, `echo '{bad' |` and `head -c 1000000 /dev/urandom |`: hint, exit 0.
4. Parse plugin/hooks/hooks.json and plugin/.claude-plugin/plugin.json with JSON.parse; matcher is "startup"; the args path exists.
5. `grep -nE "node:|fetch\(|import\(|require\(" plugin/scripts/*.mjs` is empty; the method-name scan of plugin/ is empty.
6. Field sync: `awk '/^## 3\./,/^## 4\./' docs/contract.md | grep -cw findings` and the same for each quoted name; a whole-file grep proves nothing.
7. `node --test test/plugin/` (fail 0, skipped 0, todo 0), then each other suite as above, the server one in the background (about 110 s) and read its output file; the total stays the baseline plus your tests, and any difference to the baseline above is yours to explain. On a copy of plugin/ with `touch plugin/.DS_Store`, `node --test test/plugin/` stays green; with a `plugin/marketplace.json` added it goes red.
8. Not checkable here, write "unchecked": that Claude Code fires the hook on a new session, and whether Claude uses the context or shows it to the user (needs a session with the plugin loaded, the user's step; the hooks page says to check delivery in the debug log).
9. README commands: `claude plugin configure --help` prints the flags; every shell command the README shows is one the pages give (the install and `--config` forms, `--values-stdin`, `--json`); `claude plugin validate ./plugin` still passes with warnings.
