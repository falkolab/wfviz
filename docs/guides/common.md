# Common rules for node guides (one rule per repeated, approved finding category; each names its category in brackets)

- [stale-state] A live update must patch only the nodes whose data changed and keep the rest (same DOM node, scrollTop, focus, selection): never rewrite a container's innerHTML because one part of its signature changed, so scrolled blocks inside an open pane (Result, Prompt, Changes) survive every snapshot and every transcript re-read. An interaction on a value that is shown clamped or derived (a dragged column width, a scroll offset) must start from the value displayed, not from the stored wish, and the test must run against a real DOM (same node, same scrollTop, both columns after a move), not match a regex in app.js. A value that a later record of the same synchronous hand-over will replace (a start time taken from the script file before the first agent record arrives, a status before the first event) is never published as a snapshot: the first publish waits until that whole first step has been applied (one microtask or one batch), so the first frame a client receives already holds the final value. The test records the first frame actually sent and requires the final values in it (startedAt from the first agent start, a known status), and a test is never loosened to accept `null` or `unknown` there, because that hides the stale first frame. A programmatic scroll or focus to a target (scrollTop set to a section, scrollIntoView) is a pending target, not a one-time write: while content above the target is still loading (a one-line "loading..." Changes group that grows after the transcript read), keep the target (agent, section) and apply it again after every render that can change the layout above it, until the user scrolls. The test makes that read change the height above the section and requires the section on screen afterwards, because a fixed fake layout (SEC_LAYOUT) cannot show the drift.

- [flicker] When one value changes, patch only that value's own text node or attribute: unchanged labels, badges, fact rows and siblings keep their DOM nodes, so nothing is removed and re-added with identical outerHTML. A list that only appends never rewrites an appended line: settle its fields (time, title, state) before appending, or patch just the changed cell; the test records a MutationObserver over a replay and fails on any node removed and re-added with identical content.

- [guide-defect] A guide must agree with itself and with the node spec before it is issued: its closing test line names the exact tests expected to fail (the same count and names as everywhere else in the guide and the spec) instead of saying "all pass, 0 skipped", and every value the code branches on that can be missing (a Run or list item with no source, an unknown mode) gets one explicit sentence saying whether it counts, repeated in the check for that item. A requirement about look or geometry (a panel inside the window, scrollLeft/scrollTop, scrollIntoView scrolling the page, computed style) gets a gate the node runs itself, such as a headless-Chrome DOM measurement over CDP at 800 and 1228 px without the browser pane, plus a trap line naming it, and only what cannot be measured goes to the orchestrator's ui-check as "unchecked"; adding a rule to this file is not done until every guide it touches has been re-read and edited in the same step (grep each guide for the rule's terms and list the changed lines), because a rule that no guide applies prevents nothing. A CSS shape a guide recommends or a consequence it states ("the column scrolls sideways", "breaks at the hyphen") must be a measured result of the final code, with its numbers and the condition it holds under, and the guide is not issued as final until it matches the shipped code: a fixer's owned paths exclude docs/guides, so a guide stays as first written unless the same round ends with a guide edit, which means the fixer's note lists every selector and declaration it removed or added, and a guide agent then greps the whole guide for those declarations and for every number or phrase derived from them (the same shape is restated in the owned-files list, the traps, the description of the test and the check items: `flex: 1 1 0`, `nowrap`, "15.4 px", "scrolls sideways"), rewrites each hit to the shipped rules, adds the case the fix introduced (a tag wider than its column), and lists the changed lines; a guide file older than the code it describes, with the code's declarations changed since, is itself a finding. Every width- or height-bound element also gets a check item for content wider or taller than its box (wraps, clips or overflows, and where the overflow ends up), because an unmeasured "it scrolls" or "it overflows" is the claim most likely to be wrong. The same holds for any statement about a shipped file that is not CSS: which lines a diff shows as `-`, `+` or context, how many changed lines it has, whether code is one collapsed line or a multi-line chain, is copied from the real output of `diff -u` on the shipped files, re-run after every change to those files, and the guide is edited in the same step, because a fixer that follows a stale description restores the old shape and breaks the requirement that depended on it. A character that is easy to corrupt (a superscript digit, a combining mark, any non-ASCII) is named in a guide by its code point (U+00B2, U+0300) and, where the file holds an escape, by the escape text in backticks, never pasted raw; the guide says which form each shipped file holds, checked on the bytes of every file it mentions (`od -c`, `grep -c`), and is itself scanned for non-ASCII bytes before it is issued. Before a guide is issued, every file that any numbered spec item says to change (a help line in `src/server/args.mjs`, a header comment, a test pin) is matched against the node file's `owns` and the guide's "Own" line, and a file that is missing is added to `owns` by the node-file author in the same step; a guide never hands such a file to "the orchestrator adds it or edits the line", because the orchestrator writes no product code and the implementer cannot touch what it does not own, so the item can never be done.

- [stale-test] When a node changes what a field, scope or count means (a new `scope` value, a list that now holds more kinds of items) or adds a construct that a test counts in a source file (a second `setTimeout(` or `addEventListener(` in web/app.js, a new `.innerHTML =` line), the guide agent greps `test/` for every assertion on that field or count before the node is issued, and puts each test file that asserts the old meaning into the node's owns list or, if it is outside owns or shared, lists it up front for the orchestrator with the exact new numbers and the message to change. The orchestrator makes that edit and runs the named tests before the node starts, because a guide line "the orchestrator sets it before the run" is a promise, not a state: the guide says the files must show as modified, the gate's first step checks it, and a node whose named tests are still red is not issued; the implementer and fixer run the whole test directory that reads the node's files (`test/model/`, `test/server/`), not only the node's own tests, so a stale assertion shows up in the same round, and a guide never leaves such a test red with the note "outside owns". A stale-test finding that comes back after a fixer round means the test edit was never made (the fixer rightly leaves source as it is, since moving or hiding the construct would weaken the test): it goes to the orchestrator at once as a blocker with the exact edit (file, line, old count, new count, new message naming every counted instance, e.g. all three `setTimeout(` timers: highlight, transcript re-read, copy-label reset), not to another fixer round, and the node is not re-run until `git diff --stat -- test/` shows those files changed and the named tests are green. A node that adds a new test directory (`test/plugin/`) is a stale-test case too: the suite list in `test/index.js` (and any run list that names suites) must gain the new name when the node's index.js is created, so the node file puts `test/index.js` in owns by default (the one-word edit is then the implementer's, made right after it creates the new `index.js`, and a fixer can repair it in the same round), and only a node that cannot own it lists the edit up front for the orchestrator; the gate counts `npm test` passes rising by the new suite's tests, and `node --test <new dir>` passing alone never stands in for the full run, because a suite that `npm test` never imports cannot fail the gate. A guide that records this edit as the orchestrator's "open item" has promised it, not made it: the orchestrator makes the edit before the node is sent to review, the gate's first step fails while `git diff --stat -- test/index.js` is empty or `grep` finds no new suite name in its `suites` array, and a reviewer re-checks that `grep` on the shipped tree instead of trusting the guide, so an "open item" still open at review is a blocker for the orchestrator with the exact edit (add the suite name to the `suites` array), not a fixer round; the node is not accepted until the `npm test` pass count is shown to have risen by exactly the new suite's tests (the new directory's own count, such as 24 for `test/plugin/`, never 0).

- [doc-mismatch] Every instruction a README, guide or product text gives the user (a command to run, an option to set, a behaviour to rely on) is checked before it is written against the vendor's documentation page and the tool's own `--help` output, with the version and the fetch date named, and the quoted command is run or its help printed; a test asserts only what that checked source says, never the instruction string as its own proof. The mechanism's documented cautions and limits (for example that injected context is wrapped in a system reminder, is not shown as a chat message, and imperative wording can make the model surface it to the user) go into the README for the user to decide on, and a guide lists an item under "not documented" only after the documentation was searched for it.

- [weak-test] A spec line "X happens when Y arrives" is tested once in every state the spec names for it (paused, catching up with kept frames, playing with a non-empty queue), not only in the first state a test author thinks of, and a guard the spec states ("frames behind a broken one are not shown") gets an input that is valid on its own behind the broken one (a snapshot, `end`, a later correct event), so the assertion goes red when the guard is removed. Before a test is issued, delete or invert the guard it claims to pin on a throwaway copy and confirm that test fails; a test that stays green under that mutation is vacuous and is rewritten.

- [missing-implementation] An implement step that ended `failed` (API error, dropped connection) or left the owned paths unchanged is re-run and is never sent to tests and review: before the gate starts them it checks that the implementer's journal state is not `failed`, that `git diff --stat <baseline> -- <owns>` is not empty and that each new symbol, option or endpoint the spec names exists (`grep` for `loadRun`, a new `loaded` field), and the implementer does not end its turn without a Write or Edit on an owned file and a run of the tests it added. A reviewer or ui-check that meets an empty diff reports one `missing-implementation` finding saying the diff is empty and names the baseline command it ran, never a pass or an empty finding list, because a green test run on an unchanged tree proves nothing.

- [missing-feature] Each page-visible item in a spec (a switch, a filter, a URL hash key, an extra row text, a loading or error line) is written in the spec with the exact selector, id or text and the observable result of using it, and the node's own test finds it in a real DOM or API response and drives it (click, set the hash, reload) before review; run on the baseline commit that test must be red, so the node cannot be accepted while the feature is absent. A ui-check scenario uses the same names and, when a control cannot be found, reports it once as one `missing-feature` finding with the page state it saw instead of one finding per later step it could not do.

- [stale-doc] When a node changes what an option, field or behaviour means, the node-file author greps the whole tree for every sentence that states the old meaning before the node is issued (`grep -rn -- '--since' src bin web docs README*`, which also hits help text and header comments), puts each file with such a line in `owns`, and lists the old line in the spec as a line to rewrite or delete. The new text replaces the old line and is never appended below it, and the node's check runs the real output (`node bin/wfviz.mjs --help`) and fails when two statements about the same option disagree: a `HELP_NOTE` printed after a `usage()` line that still says `--since ... (default: 24)` is a finding by itself. A node whose spec needs a file outside `owns` is not issued, and is never accepted with the note "outside owns, the orchestrator edits the line" (the orchestrator writes no product code); a guide line that records such a file as an "open item for the orchestrator" is itself a defect, and a stale-doc finding that comes back for that reason is closed by adding the file and its test (`src/server/args.mjs`, `test/server/args.test.mjs`) to `owns` and running a fixer round. The `usage()` line is rewritten to the new meaning, never left for a later note to contradict, because a usage error prints `usage()` without `HELP_NOTE`; the check therefore runs both `node bin/wfviz.mjs --help` and a bad-option call.

- [gate-passes-empty-diff] A sentence "the gate checks X" is not in force until `workflows/gate/gate-template.js` contains the check and `test/workflows/gate-template.test.mjs` has a test that is red without it. The pass line (`!approved.length && testsOk(tests)`) also requires that the implement step returned a result and that `git diff --stat <baseline> -- <owns>` is not empty; otherwise the status is `blocked` with the reason `implementer returned nothing`, never `pass`, however many reviewers find 0 issues and however green the baseline suite is (the `missing-implementation` rule above is only a promise until this code exists). The test feeds the template an implementer that returns null on an unchanged tree and requires a status other than `pass`. A finding in this category is the orchestrator's blocker, not a fixer round, because the template is outside every node's owns: the orchestrator changes the template, adds the test and regenerates the run script with `tools/make-dev-graph.mjs` before the next run is started, not after the finding comes back, and until then checks `git diff --stat <baseline> -- <owns>` by hand before accepting any node's `pass`. The status is derived from every failure the report records, not from reviewers and tests alone: a report that says `implement: 'implementer returned nothing'` next to `status: 'pass'` is the defect in one line.

- [layout] Whatever an action must show the user (a notice, an excerpt, a hit's where-line, a close button) is placed or raised above every `position: fixed` or `position: absolute` panel that can be open in the same state (the agent drawer, the run result pane), or the action closes that panel first, and the node's own test opens the panel on the run on show, runs the action, and requires the target to be the topmost element (`elementFromPoint` at its centre) in headless Chrome at 375, 800 and 1228 px. A fake page has no stacking, so a DOM-only test that starts with the panel closed cannot see the cover and never stands in for that measurement.
