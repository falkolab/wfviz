# Node guide: replay in app (unit replay-in-app)

Read with docs/guides/common.md: [stale-state] and [flicker] (the replayed view is patched by key like the live view), [stale-test] (the tests named below), [guide-defect] (geometry is measured, not assumed). The spec (items 1-5) is in the node task; this file says what binds, what you may break, where it is easy to go wrong, and how to check. Facts below were measured on 2026-11-10 on a throwaway copy of the repo outside the project.

## Rules that bind
- docs/contract.md, intro: "wfviz is universal"; no role, phase, label, node code, file name or result shape of our method "may be required or hard-coded" in src/, web/, bin/. Replay works for any run, free labels included; no control text names our method.
- contract section 1, Replay: events are re-emitted "every value unchanged (ts included)", the pace is the source's, "Replay never mixes with real or demo events". "Replay inside the real server": the replay has "a **separate** store of its own: its events and its Run (`source: "replay"`) never enter the server's real store, its run list or `/api/stream`. Only a run whose status is final (not running) can be replayed; ... closing stops its timers. Pause is the client's".
- contract section 4: the `GET /api/runs/:id/replay?speed=<n>` line (hello, run, event, end; 404, 409, 400, 429; "Read-only: it reads the run's files and writes nothing"), `/api/stream` "`seq` per run, from 1, no gaps", "Server binds `127.0.0.1`". Section 5: the launcher exits "after --idle seconds with no SSE client". Section 5 does not list the `replays` option; this node adds it, the contract is not yours to edit.
- AGENTS.md, Hard rules: "Never invent data"; "The visualizer only observes: no endpoint writes, stops or starts anything"; "Demo data never mixes with real data"; "Write only the files your node owns"; no git commit, stash or reset; ES modules, Node >= 20, zero npm dependencies. graph.md section 9: "Workflow agents must stop only the processes they started, by PID" (start wfviz with --no-open, stop it with kill <pid>); never the browser pane (task rule), headless Chrome over CDP for geometry as in common.md.

## Traps: server (src/server/server.mjs)
- Order of checks, decided and tested pairwise: mode not real or `replays` absent -> 404 `{error:'not found'}`; method not GET -> 405 Allow GET (HEAD too, as /api/stream); bad speed -> 400; run not in the REAL store (visibleRun) -> 404 `{error:'run not found'}`; status running -> 409 with the reason; 3 replays open or being prepared -> 429 (the fourth is refused, a closed one frees its slot, a prepare that is still reading holds one); then `prepare`. Speed absent: pass undefined (the source defaults to 4, the server invents no default). Present: the DECIMAL regexp of args.mjs (copy it, name args.mjs in a comment), finite and above 0. Measured: '', ' ', '0', '-1', '+1', '0x10', 'abc', 'Infinity', '1e999' refused; '0.25', '.5', '1e2', '500' pass (the source clamps to 100). A repeated `speed=1&speed=2` is a 400 (decide, name, test).
- Running: one helper, the status Fact's value is the text "running" -> 409; every other value counts as not running, a null or unknown value too (a stale run, or one whose journal is not read yet). Contract 1 says "status is final (not running)"; the spec says "not running", so the test is on `value`, never on `prov`. The web uses the same rule.
- Replay streams are NOT in `clients`: the real onStoreChange and onStoreEvent write to every member of that Set, so a replay stream in it would get the real snapshots and real events of the same run id with the real seq. Keep a second Set. The combined size goes to onClientCountChange (idle shutdown counts it), the heartbeat covers both Sets (stops only when both are empty), `endStreams` ends both. Reuse the throttle code through a record that holds its own latest Run; do not paste a second copy.
- `visible()` drops a Run whose source is not "real", so the replay path needs its own check: send a snapshot only if `run.source === 'replay'`, else drop it and call onError (a real Run can never leave through this route). Throttle as /api/stream (`throttleMs`): the first change goes now, changes inside the window coalesce, the trailing send carries the LAST thing given to onRun (the server has no store to ask); timers unref'd and cleared on close. `onRun` is given a Run, or a function that builds the newest Run: the server calls the function only inside the send (inside `safe`), so a replay that changes its Run at every event builds one Run per snapshot that goes out, not one per event (measured on a 73 MB run of 2137 events: a Run built at every event cost 18.3 s of CPU for one replay; with the function, three replays at once cost 3.8 s of CPU in the server in all and /api/runs answered in about 1 ms meanwhile). At the end: cancel the timer, send the latest snapshot (the function is called once), write `end` {runId, events} (events = the `event` frames this stream carried, never renumbered), then end the response so the slot is free and nothing waits for a reconnect.
- open() re-entrancy: register the record and the response `close` listener BEFORE calling open(); a fake calls back synchronously, and the client may be gone before the handle exists (stop at once when it arrives). stop() runs once however many of close, server.close(), end and error happen. After stop nothing is written. An open() that throws or an onError ends the stream WITHOUT `end` (the contract names no error event: do not invent one), goes to the server's onError, still stops once. All writes through writeTo.
- Failures that can be known before the stream starts are not stream failures: `replays.prepare({ runId })` (optional, awaited before the 200 and the `hello`) finds and reads the run, and its rejection is a JSON answer with the reason, never a `hello` first: the status is the error's own `status` when it is an integer 400..599 (the launcher sets 404 for a lookup that finds nothing or two places, and for a run with no event), else 500 (also reported to onError; a 4xx is an answer, not a fault). What prepare resolves with is `prepared` in open(). Holding the slot: a pending prepare counts toward the limit of 3 until it answers (also when its client left: the reading still runs), a client that left meanwhile gets nothing and nothing is opened, a server that closed meanwhile answers 503. Only what can first go wrong after the `hello` (the source's start() failing late, a throw inside the replay) still ends the stream with no frame that carries the reason: that is a gap in contract section 4 (no error event) which this node does not close; it goes in the note to the orchestrator, no error event is invented.

## Traps: launcher (bin/wfviz.mjs)
- `replays` only in real mode (never in the WFVIZ_TEST_FAKE parts, demo, or --replay). Pass the createStore already imported in loadParts, never a second import of reduce.mjs. One store per open, `createStore({ staleMs: Infinity })` (arms no stale timer); unsubscribe its onChange and onEvent in stop(). The store's onChange calls `onRun(latest)` with `latest = () => store.getRun(id)`: never `store.getRun` inside the change handler (it re-reduces the whole run, O(n^2) over the run, and the server's throttle throws nearly all of it away).
- Lookup: `locateRun({ target: runId, root })` with the real source's root (`path.resolve(opts.root)`, or undefined for the default). locateRun reads a name with a separator as a path, so refuse a runId with `/` or `\` first. All of it, and the read (`readRunDir` once, no events is an error), happens in `prepare`, before the server says hello: a ReplayLookupError or an empty run is rejected with `status` 404 (its message is the reason the page shows), any other read failure is rejected as it is (the server answers 500). Only a start() rejection after prepare (the source's own late failure) is an onError of the stream.
- The end: replay.mjs has no end signal (needed change, not yours: an `onEnd` option; use it if it exists). Until then pass createReplaySource its documented `readRun` option, a function that gives back the events `prepare` already read (the run is read once per replay, not twice), count the events the source hands to its onEvent and call onEnd when the count reaches `events.length`, after the last one. Do not guess the end from run.final or from a timer.
- Sink: only `src === 'replay'` goes into the replay store (others dropped, one warning like guardedSink). Never give a replay event to the real edit-input tracker (same run id as the real run: its transcript entries would be added to) or to the real store. After stop() nothing calls back; the source's stop() clears its timer, also while it still reads.

## Traps: web
- Read the stream with fetch and a reader, not EventSource: EventSource cannot read the status or the JSON body of a 404, 409, 429 or 400 (the page must show the reason) and reopens a closed stream by itself, so a finished replay would start over. A pure parser in lib.js turns text chunks into frames (event name, JSON data; a frame split over two chunks waits; `: heartbeat` lines ignored; TextDecoder with `stream: true`). JSON.parse of a frame inside try. One AbortController per replay; an abort the page made (Stop, another run, Replay again) shows no error. A stream that ends without `end` shows "stream ended before the end" with the count so far.
- The replay stream is its own thing: its `hello` never reaches renderMode, state.mode or state.hellos (check its mode is "replay" and its runId the requested one, else a line); its `run` frames never reach state.runs (mergeRun would turn the real run's picker row into a replay row); its `event` frames never go through onLiveEvent (its gap path reads the REAL store's backlog). While a replayed view is on screen (`state.replay.shown`: from the hello, and from the click of Replay again, see below), the real stream's `run` and `event` for the run on show change nothing but the picker row, and a real-stream reconnect does not call selectRun for it.
- State is one object `state.replay` (null, or runId, speed, phase connecting/playing/paused/ended/failed, shown, begun, real, buffer, abort, closed, endSeen, count, line). Two flags, not one: `begun` = the stream has said its right hello (its frames are accepted, the view is cleared for it); `shown` = the view on screen is a replayed one (REPLAY mark, banner, Stop, and the real stream ignored all follow it). A replay started on the real view has `shown` false until the hello (the real view stays on screen meanwhile); a replay started on a replayed view (Replay again, after the end or after a failure that had begun) is `shown` true from the click, so that the old replayed view stays on screen with its mark and Stop until the new hello clears it, and a refusal (429, 409, 404, the network, a cut or wrong stream) leaves a replayed view that has its mark and a way back, never a replayed view with no mark and the real stream writing into it. The mark is on exactly the replayed view. At the hello (`beginReplayView`): bump state.sel (a selectRun in flight would draw the real Run over the replay), closeDrawer(), state.log.reset(id) then state.log.load([]) (a log that is not ready only holds pushes), state.run = null. A null run before the first snapshot must not print "No workflow runs found in the watched directory yet.": give renderEmpty a message parameter (one setHtml call, so the web-u4 list holds; setText on #matrix-empty would break setHtml's cache). Stop, also after the end: abort, state.replay = null, selectRun(runId) re-reads the real Run and log. Choosing another run stops the replay first, no re-read of the old one.
- Control state is one pure function in lib.js (inputs: the real Run on show, kept in state.replay while replaying, and the phase). Replay shows only when run.source is exactly "real" and the status value is not "running": a Run with no source gets no control, an unknown status (null value) gets it, the server mode is not read. Connecting or playing: Pause, Stop. Paused: Resume, Stop. Ended: "replay finished", Replay again, Stop (back to the real view). After an error: the reason line and the Replay control, the line stays until the next click or a run switch; when the failed replay had a replayed view on screen (`shown`), the control is Replay again with Stop and the mark stays. Errors come from `{error}` of the body, else fetchErrorText.
- Pause buffers every frame in arrival order and applies none: events in order, but only the newest `run` snapshot (older ones are superseded; all of them would be a multi-megabyte Run per second) and the `end`. Resume applies the events through the live path (state.log.push, appendLog, flashAgent), then the snapshot, then the end. Stop or a run switch drops the buffer; frames that arrive after it are ignored (token compare). Pure buffer in lib.js, tested for order, newest snapshot, end kept, empty resume.
- Chrome: the banner is the existing #replay-banner; renderMode sets it from the server mode, so it shows when the mode says replay OR the replayed view is on screen (`state.replay.shown`; a reconnect hello must not hide it). A static REPLAY mark with the `.badge.replay` look and the text of modeInfo('replay') sits next to the picker; the #mode badge keeps the server's mode. The replayed Run has source "replay": clockTick is null (no interval) and its status reads running until the final event, as the model says; do not rewrite it.
- Drawer: the transcript endpoint serves the finished real run, i.e. activity that has not happened yet at the replay's time. While replaying do not call it (loadTranscript, scheduleTranscript) and have the Changes section say that edit inputs are not available in a replay instead of "loading..." forever; the activity list comes from the replayed agent.activity.
- Escaping and storage: the reason text and the run id are data (setText for the line, esc() in any spec string, no innerHTML). Speed: control values 1, 4, 20 only; `localSet('replay.speed', ...)`; one pure parse (null, '', 'abc', '0', '100' -> 4); the URL gets a number you built, not the stored text. Geometry: static markup with `hidden`; in headless Chrome over CDP at 800 and 1228 wide measure header height with a finished real run on show with and without the control, no overlap with the picker; put the numbers in your note.

## How to check each item by hand
Start `node bin/wfviz.mjs --no-open --idle 0 --root fixtures/claude-projects --since Infinity`, keep its PID, read the port from stdout, stop it with kill <pid>. Never --demo in place of real data.
1. `curl -sN -m 8 "http://127.0.0.1:$PORT/api/runs/wf_6509ce25-20a/replay?speed=100"`: `hello` {mode:"replay",version,runId} first, `event` seq 1..31 without gaps, `run` frames with "source":"replay", the last `run` completed, then `end` {runId,events:31}, then the stream closes. wf_26eb8d70-5c4: 35 events, failed. Measured at speed 100: about 2.1 s and 1.1 s.
2. Codes with `curl -s -o /dev/null -w '%{http_code}'`: speed=abc, 0, -1, empty, 1e999, Infinity -> 400; unknown id -> 404; the same route on a `--demo` server and on a `--replay` server -> 404; a temp root holding one fresh journal-only run -> 409 with the reason; three background curls at speed=0.25 (keep their PIDs) then a fourth -> 429, and after one of them is killed the next is 200; on a copy of fixtures/claude-projects with the run directory of wf_6509ce25-20a removed (its final file stays, so the run is in the list) the same curl gets 404 with `Content-Type: application/json` and `no run ... under ...` in the body, and no `hello` (the stream never started).
3. Untouched real side: a background curl on /api/stream while a replay runs shows no `event` frame and no "replay" source; /api/runs/wf_6509ce25-20a still says source real and its /events has the same length as before.
4. Close and idle: kill a slow replay's curl: no frame is written to it afterwards (test: stop() once, no timer left, with `globalThis.setTimeout` and `clearTimeout` wrapped to record the server's handles and a throttleMs of 60000); `server.close()` ends every open replay. With `--idle 1` the process outlives a closed /api/stream client while a replay stream is open and exits about 1 s after the last stream is gone.
5. Web, on the fake page (boot on real, then a finished real Run): Replay shows; a running Run, a Run with source demo or none: no control; a fake fetch returning a reader: frames drawn from empty; 409 body, wrong hello, cut stream, `end` (fetch called once, "replay finished", no reconnect); Pause then Resume (events in seq order, newest snapshot only); Stop (abort, two reads of the real Run); another run in the picker stops it; a real `run` frame for the run on show during a replay changes nothing; Replay again after the end, refused with 429, 409, 404 and a failed fetch: the mark, the banner and Stop stay, the replayed log and Run stay, the reason is the line, and a real `run` or `event` for the run still changes nothing; Stop then reads the real Run again. A MutationObserver over 20 frames sees no node removed and re-added with identical content, as the existing flicker tests do.
6. Mutate the status rule in the server and in lib.js: the 409 test and the control test turn red.
7. `node --test test/server/ test/integration/universal.test.mjs`, then `node --test test/` (about 90 s): measured baseline tests 1064, pass 1064, fail 0, skipped 0, todo 0. After your edit tests = 1064 plus your new tests, all pass, fail 0, skipped 0, todo 0; the one test that goes red before you edit it is the bin.test.mjs "source discipline: the replay module ..." above, and no other existing test may be changed except to follow the spec.
