## Traps
- Inventing values: the expected result of the example comes from running the reference; counts in your note come from running the tests; a mutant "fails" or "passes" only as `nodeTest` shows. Re-run the `x2` and `fine` results above on the shipped files.
- Escapes: every file of the node holds the escape as ASCII text, not the character, and so does this guide. TASK.md has `"x\u00b2"` (backslash, u, 00b2) in a code span; src/slugify.mjs has the regex `[\u0300-\u036f]` with one backslash per mark; in adversarial.test.mjs REFERENCE is a template literal, so the same regex is written there with two backslashes (`\\u0300`) and the file it writes has one. A model or editor may normalise a literal superscript two to `2` or the ligature to `fi`, and then the example discriminates nothing; a combining mark is invisible in an editor. Keep the forms as they are: (a) two backslashes in a real src file make the class match a backslash, `u` and a range of ASCII characters, and the starting code fails 8 of 9 visible tests instead of 5 (measured on a copy), which changes the seed; (b) a real combining mark in the starting src (or in REFERENCE) still passes and fails the same visible tests, but the two files then differ, and the minimal-fix test fails on "the minimal fix is the reference with the violation put back" (measured on a copy: that test alone fails). Evaluate the example as a JS string literal (or `JSON.parse` of the quoted text), not through the shell; in a single-quoted shell string the escape stays an escape (command in "How to check", item 3).
- No hint: nothing in TASK.md, the visible tests or the starting code says untested, hidden, seeded or "NFD is wrong"; the unit and rule are named only in the comment at the top of the new tests. The existing TASK.md sentence "incomplete or contains a bug" stays.
- Coupling: nothing in src/, web/, bin/ may name target-a or this rule; no file in the target may name a node code, a loop role or wfviz.
- Tie the minimal-fix mutant to the starting code: assert that the starting src and the mutant both contain `normalize('NFD')`, that the mutant equals the reference with `'NFKD'` replaced by `'NFD'`, that it has the reference's pass count with fail 0 and skipped 0, that its result for the TASK.md example differs from the expected one, and that `diff -u` of the starting file against it has a `-` or `+` line with `normalize('NFD')`. Take the example from rule 3 of TASK.md at test time (`slugifyRule3Example` parses each pair "`"input"` ... becomes `"result"`" of the rule as JSON strings and requires exactly one pair on which NFKD and NFD differ), so a changed, dropped or doubled example fails the test. The starting src must also give the wrong result and fail at least one visible test.
- Missing values: `nodeTest` returns null for a count whose summary line is missing. Assert numbers (`assert.equal(res.fail, 0)`, `res.pass > 0`): both fail on null. Never `!res.fail`, which passes on null.
- Hygiene (no UI, timer or listener here): copy into `scratch` under new unique directory names (the existing ones are `mutant` and `mutant-<unit>-<index>`), leave the `before` and `after` hooks alone, use `nodeTest` (drops NODE_TEST_CONTEXT, 60 s timeout), import a variant by `pathToFileURL` of its own directory. New tests go after the REFERENCE, `refDir` and `nodeTest` definitions. Running the tests must leave no GUIDE.md or .wf in demo/targets/target-a; a live run of A goes only on a copy.
